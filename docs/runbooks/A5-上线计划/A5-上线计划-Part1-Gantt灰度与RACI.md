## A5.1 上线总策略

### A5.1.1 三大原则

| 原则 | 释义 |
| --- | --- |
| **业务不中断** | 试点先行、灰度切流、双写对账，绝不"一刀切" |
| **可回退** | 每次切流/灰度前必须存在已验证的回退方案（数据快照 + 切换脚本 + RTO 目标） |
| **可观测** | 全链路埋点 + 业务北极星指标看板，异常 5 分钟内告警、30 分钟内处置 |

### A5.1.2 五阶段总路径

```
T-12 ~ T-8 周   阶段 1: 试点迁移 + 双写校验
T-8  ~ T-4 周   阶段 2: 全量迁移 + 业务切流准备
T-4  ~ T-1 周   阶段 3: 并行运行 + 对账 + 演练
T-1  ~ T+0      阶段 4: 灰度切流 + 上线日 (Go-Live)
T+0  ~ T+4 周   阶段 5: 新系统单跑 + 老系统只读 + 退役
T+4  ~ T+12 周  阶段 6: 优化 + 老系统归档
```

### A5.1.3 与 A4 迁移阶段的关系

| 阶段 | 本 A5 视角 | 配套 A4 视角 |
| --- | --- | --- |
| 1 | 选 1-2 个 BU 试点，组织 + 项目切入 | 完成试点 BU 的数据迁移 + 双写校验 |
| 2 | 培训先行，全员赋能；冻结老系统大改 | 全量数据迁移、字段映射全面落地 |
| 3 | 全员并行使用，UAT 收尾 | 对账 + 差异处理 + 回退演练 |
| 4 | 灰度切流 + 上线日 | 老系统转只读 |
| 5 | 新系统为唯一真实源 | 老系统归档准备 |
| 6 | 优化 + 老系统退役 | 数据归档、清理、销毁 |

### A5.1.4 切流模式选择

| 模式 | 适用 | 风险 | 采用 |
| --- | --- | --- | --- |
| **一刀切（Big Bang）** | 小规模、用户少 | 极高 | ❌ 不采用 |
| **分批切流（Phased）** | 中等规模、可分组 | 中 | ✅ 主采用 |
| **并行运行（Parallel）** | 大型、关键 | 低、代价高 | ✅ 阶段 3 必做 |
| **试点先行 + 灰度** | 推荐组合 | 低 | ✅ **本项目采用** |

## A5.4 灰度发布与切流策略

> 核心思想：**"先 BU、再功能、再流量"三维度灰度**，RTO ≤ 30min、RPO ≤ 5min，全过程可一键回退。

### A5.4.1 灰度三维模型

```
        维度 1：按 BU 灰度（5% → 30% → 70% → 100%）
            ×
        维度 2：按功能灰度（只读 → 写 → 流程 → 全量）
            ×
        维度 3：按流量灰度（5% → 20% → 50% → 100%）
```

> 三个维度并行推进，任意一维触发"熔断阈值"即一键回退到上一稳定态。

### A5.4.2 灰度 4 阶段（B1 ~ B4）

| 阶段 | 周期 | BU 范围 | 功能范围 | 流量比例 | 决策门槛 | 升级条件 |
| --- | --- | --- | --- | --- | --- | --- |
| **B1 试点验证** | W6-W7 | 1-2 个试点 BU | 只读功能 | 5% | 无 P0 故障，监控全绿 | 推进 B2 |
| **B2 写功能开放** | W12 末 T-0.5d | 30% BU（+ 试点） | + 写功能 | 20% | 无 P0，错误率 < 0.5% | 推进 B3 |
| **B3 流程+全功能** | T+0 D+1 | 70% BU | + 流程引擎 + 集成 | 50% | 错误率 < 0.3%，P95 ≤ 1s | 推进 B4 |
| **B4 100% 切流** | T+0 D+3 | 100% 全 BU | 全部功能 | 100% | SLO 全项达标 | 进入稳态 |

### A5.4.3 按 BU 切流清单

#### A5.4.5.2 切流配置（Nginx 片段示例）

```nginx
# /etc/nginx/conf.d/pms_canary.conf
split_clients "${arg_user_id}" $canary_bucket {
    5%      "pms_canary";     # B1 阶段：5%
    20%     "pms_canary";     # B2 阶段：20%（覆盖 5%）
    50%     "pms_canary";     # B3 阶段：50%
    *       "pms_stable";
}

upstream pms_stable {
    server backend-stable:8088 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

upstream pms_canary {
    server backend-canary:8088 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

server {
    listen 80;
    server_name pms.example.com;
    location /api/ {
        proxy_pass http://$canary_bucket;
        proxy_set_header X-Canary-Bucket $canary_bucket;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

#### A5.4.5.3 切流脚本（Shell 模板）

```bash
#!/usr/bin/env bash
# cutover.sh - 灰度切流一键脚本
# 用法: ./cutover.sh <stage> <bucket>     # stage=B1|B2|B3|B4, bucket=5|20|50|100
set -euo pipefail

STAGE="${1:?用法: $0 <B1|B2|B3|B4> <bucket_pct>}"
BUCKET="${2:?用法: $0 <stage> <bucket_pct>}"

echo "==> 切流开始: stage=$STAGE, bucket=${BUCKET}%  $(date -Iseconds)"

# 1. 预检
./preflight_check.sh "$STAGE" || { echo "预检失败，禁止切流"; exit 1; }

# 2. 更新 Nacos 配置（canary.bucket.percent）
curl -X PUT "http://nacos:8848/nacos/v1/cs/configs" \
  -d "dataId=pms-canary-bucket" \
  -d "group=PMS" \
  -d "content=${BUCKET}"

# 3. 触发 Nginx reload（Lua 共享内存更新）
./reload_nginx.sh

# 4. 等待 60s 观察
sleep 60
./health_check.sh "$STAGE" || {
  echo "切流后健康检查失败，触发回退"
  ./rollback.sh "$STAGE"
  exit 2
}

# 5. 记录切流日志
./log_cutover.sh "$STAGE" "$BUCKET" "success"

echo "==> 切流成功: stage=$STAGE, bucket=${BUCKET}%  $(date -Iseconds)"
```

## A5.5 回退预案（Rollback Plan）

> 核心目标：**RTO ≤ 30 分钟，RPO ≤ 5 分钟**，一键回退到上一稳定态。回退与灰度切流互为镜像（A5.4.5.3 的 `rollback.sh` 调用本节剧本）。

### A5.5.1 回退总体策略

| 维度 | 设计 |
| --- | --- |
| **触发方式** | 自动（监控阈值 F-1~F-10） + 手动（值班一键）双通道 |
| **决策权** | 切流指挥部授权 → 切流指挥 B/C 5 分钟内决断 → 通报 PMO 总监 |
| **回退粒度** | 接口级 / BU 级 / 全量级（L1/L2/L3，见 A5.4.6.2） |
| **数据保护** | 切流前 1h 增量 WAL + 全量 baseline 快照，保留 ≥ 30 天 |
| **回退方向** | 单向向下（B4→B3→B2→B1→老系统），不回跳 |
| **回退后观察** | 至少 30 分钟稳态观察期，期间不重新升级 |

### A5.5.2 回退决策树

```

                       │
                       ▼
              ┌────────────────────┐
              │  切流指挥收到告警   │  (≤ 2 min 响应)
              │  + 影响范围评估     │

                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
         单接口        单 BU        全局
         (F-1~F-3)   (F-1~F-7)    (F-1~F-10)
            │           │           │
            ▼           ▼           ▼
         L1 熔断     L2 回退      L3 回退
         Sentinel   切回老系统    全量回退

            │           │           │

            │           │           │
            └───────────┴───────────┘
```

#### A5.5.3.1 L1 — 单接口熔断（接口级）

| 项目 | 内容 |
| --- | --- |
| **触发** | Sentinel 检测 F-1/F-2/F-3 在单接口触发阈值 |
| **决策** | 自动（无需人工） |
| **动作** | Sentinel 规则 `degrade` 该接口 → 返回兜底数据（缓存 / 老系统代理） |
| **RTO** | ≤ 1 min |
| **影响** | 仅该接口；其他接口正常 |
| **升级条件** | 5 min 内未恢复 → 升级 L2 |
| **剧本** | `playbook_L1_interface.sh` |

#### A5.5.3.2 L2 — BU 切回老系统（BU 维度）

| 项目 | 内容 |
| --- | --- |
| **触发** | F-1/F-2/F-3/F-6/F-7 在某 BU 集中 |
| **决策** | 切流指挥 B（≤ 5 min 决断） |
| **动作** | Nginx Lua 将该 BU 的 `user_id` 段切回 `pms_stable`（老系统） |
| **RTO** | ≤ 10 min |
| **影响** | 该 BU 全部用户回老系统，其他 BU 继续使用新系统 |
| **数据处理** | 回退期间该 BU 的"新系统数据"标记为 `dirty=true`，事后回灌 |
| **升级条件** | 影响扩散到 ≥ 2 个 BU → 升级 L3 |
| **剧本** | `playbook_L2_bu.sh <bu_code>` |

#### A5.5.3.3 L3 — 全量回退（切流级）

| 项目 | 内容 |
| --- | --- |
| **触发** | F-1~F-10 任意严重，或 L2 升级，或高管决策 |
| **决策** | 切流指挥 + PMO 总监（≤ 10 min 决断） |
| **动作** | Nacos 配置回退到上一阶段 + Nginx 全量回 `pms_stable` + 老系统转活跃 |
| **RTO** | ≤ 30 min |
| **影响** | 全部 BU 回老系统 |
| **数据处理** | 全量回灌 + 双写对账 |
| **升级条件** | — |
| **剧本** | `playbook_L3_full.sh` |

#### A5.5.4.3 回灌脚本骨架

```bash
#!/usr/bin/env bash
# replay_bu.sh - BU 维度数据回灌
# 用法: ./replay_bu.sh <bu_code> <from_ts> <to_ts>
set -euo pipefail

BU_CODE="${1:?用法: $0 <bu_code> <from_ts> <to_ts>}"
FROM_TS="${2:?from_ts (ISO8601)}"
TO_TS="${3:?to_ts (ISO8601)}"

echo "==> BU ${BU_CODE} 数据回灌开始: ${FROM_TS} -> ${TO_TS}"

# 1. 暂停该 BU 在新系统的写
./freeze_bu_writes.sh "$BU_CODE"

# 2. 导出该 BU 在新系统的 dirty 数据
./export_dirty.sh "$BU_CODE" "$FROM_TS" "$TO_TS" > /tmp/dirty_${BU_CODE}.jsonl

# 3. 转换到老系统 schema
./transform_to_legacy.sh /tmp/dirty_${BU_CODE}.jsonl > /tmp/legacy_${BU_CODE}.jsonl

# 4. 导入老系统（带事务，失败回滚）
./import_to_legacy.sh /tmp/legacy_${BU_CODE}.jsonl || {
  echo "回灌失败，保留 dirty 数据待人工处理"
  exit 3
}

# 5. 双写对账
./reconcile_bu.sh "$BU_CODE"

# 6. 解除新系统冻结
./unfreeze_bu_writes.sh "$BU_CODE"

echo "==> BU ${BU_CODE} 数据回灌完成"
```

### A5.5.8 回退决策的反模式（Anti-Patterns）

| 反模式 | 后果 | 规避 |
| --- | --- | --- |
| 多次小幅回退 | 用户困惑、监控抖动 | Hold 30 min 不重新升级 |
| 回退不通报 | 业务方不知情、舆情 | 强制通报链路 |
| 数据不回灌 | 后续审计缺失 | 强制 `replay_*` 任务 |
| 回退后不修复就重启 | 同一问题复发 | Postmortem 必须有 Owner + DDL |
| 跳过回退决策 | 故障扩大 | 切流指挥无授权禁止操作 |

### A5.5.9 回退与 A5.4 灰度的关系

```
A5.4 灰度切流 (前进)     ⇄     A5.5 回退预案 (后退)
   B1 ──▶ B2 ──▶ B3 ──▶ B4          B4 ──▶ B3 ──▶ B2 ──▶ B1
                                          │
                                          ▼
                                    老系统 (L3)
```

- **镜像设计**：回退脚本 = 切流脚本的反向操作
- **状态保持**：每次前进/后退都记录 stage → 允许跳级回退（如 B4→B1）
- **数据一致性**：回退到任何阶段都触发"该阶段之后的 dirty 数据回灌"

## A5.6 RACI 责任矩阵

### A5.7.5 风险处置 4 策略（TAMR）

| 策略 | 适用 | 操作 | 成本 |
| --- | --- | --- | --- |
| **T 接受（Accept）** | L3/L4 低风险 | 记录 + 监控 | 极低 |
| **A 规避（Avoid）** | 可消除 | 调整方案 / 取消 | 中 |
| **M 缓解（Mitigate）** | L0~L2 | 实施控制措施 | 高 |
